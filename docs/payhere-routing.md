# PayHere routing

Bank-core `6eabafe` uses one `payhere.server-base-url` property for browser launch links, browser return and cancel links, and provider notification URLs. The example configuration binds this property from `PAYHERE_SERVER_BASE_URL`. All paths in the first table belong to the bank-core origin. Bank-web answers requests in `/api/v1/wallet/payhere` and `/api/v1/wallet/webhook`, including descendants, with a local noncacheable `404` and sends nothing upstream. This keeps bank-core HTML off the web session origin and keeps provider POSTs independent of the browser session.

## Direct bank-core routes

| Method and path | Caller and request | Implemented response |
| --- | --- | --- |
| `GET /api/v1/wallet/payhere/checkout/{intentId}` | Browser follows an intent link. No session, body, or request content type. | `200 text/html` auto-submits an order form to PayHere Checkout. The stored intent supplies the order ID, amount, and currency. The handler has no explicit missing-intent response. |
| `GET /api/v1/wallet/payhere/preapprove/{sessionId}` | Browser follows a card-session link. No session cookie, body, or request content type. | `200 text/html` auto-submits a preapproval form to PayHere. A missing or consumed session yields an HTML expiry message. |
| `GET /api/v1/wallet/payhere/return` | Browser navigation, optional `intentId` query. No session or body. | `200 text/html` uses a meta refresh to `PAYHERE_APP_DEEPLINK` with the supplied intent ID when present. |
| `GET /api/v1/wallet/payhere/cancel` | Browser navigation, optional `intentId` query. No session or body. | `200 text/html` uses the same deep link and appends `canceled=1` when the intent ID is present. |
| `GET /api/v1/wallet/payhere/cards/return` | Browser navigation, required `sessionId`, optional `status` or `status_code`. No session or body. | `200 text/html` sends the browser to `PAYHERE_APP_CARD_DEEPLINK` with an encoded session ID and the supplied status or default `2`. This is a navigation hint. |
| `GET /api/v1/wallet/payhere/cards/cancel` | Browser navigation, required `sessionId`. No session or body. | `200 text/html` sends the browser to the card deep link with the encoded session ID and `status=CANCELED`. |
| `POST /api/v1/wallet/payhere/notify` | PayHere server, `application/x-www-form-urlencoded`. The signature check uses `merchant_id`, `order_id`, `payhere_amount`, `payhere_currency`, `status_code`, and `md5sig`. No customer cookie, JWT, or CSRF token. | `200` with `invalid` for a failing signature or `ok` for a valid signature, including an unknown order. A matching order updates the intent status and copies `status_message` into its description. |
| `POST /api/v1/wallet/payhere/notify/preapprove` | PayHere server, same form encoding and signature check. Core reads `customer_token`, `recurring_token`, or `token`, plus `method`, `masked_card` or `card_no`, and `card_expiry`. No customer cookie, JWT, or CSRF token. | `200` with `invalid`, `ignored`, `unknown-session`, `already`, or `OK`. A successful notification for an unconsumed session stores a card token and consumes the session. A valid non-success notification consumes any matching session. |
| `POST /api/v1/wallet/webhook` | Disabled legacy route, outside the PayHere flow. Spring requires authentication. The handler binds `intentId` and `status` as request parameters. | `410` from the handler with the required parameters. No state change. |

Returns and cancels change no stored payment or card state. PayHere Checkout sends payment status to the notification URL. Bank-core maps `2` to `SUCCESS`, `0` to `PROCESSING`, `-1` to `CANCELED`, and the other codes, including `-2` and `-3`, to `FAILED`. A browser return means the user came back, and a cancel link describes that navigation. The owner-scoped intent status is the backend read for a future payment screen, subject to the callback checks below. See [PayHere Checkout](https://support.payhere.lk/api-%26-mobile-sdk/checkout-api) and [PayHere Preapproval](https://support.payhere.lk/api-%26-mobile-sdk/preapproval-api).

## Authenticated wallet API context

These `/api/v1/wallet` paths may use the same-origin BFF. Spring requires `CUSTOMER` and the wallet service scopes records to the authenticated user. Requests use the HttpOnly session cookie and state-changing requests require the CSRF header. The BFF injects the Bearer token server-side.

| Method and suffix under `/api/v1/wallet` | Request and response |
| --- | --- |
| `GET /cards` | `200` JSON with card IDs, brand, last four digits, default status, and creation time. The stored provider token stays in core. |
| `POST /cards/session` | Optional `returnUrl` request parameter, currently ignored by core. `200` JSON with session ID and a direct preapproval URL. |
| `PATCH /cards/{id}:default`, `DELETE /cards/{id}` | No request body. `204` after the service handles the card. |
| `POST /payments/qr`, `POST /payments/reload`, `POST /payments/bill` | JSON with `amount` (`value` and `currency`). The DTOs also accept `qrData` and `merchantRef`, `msisdn`, or `billerId` and `reference`, respectively. The current service uses the amount and payment type to create a `PROCESSING` intent. It accepts an optional `Idempotency-Key`. `200` JSON includes the direct checkout URL. |
| `GET /payments/{intentId}` | `200` JSON for the owner, `404` for an absent or non-owned intent. The DTO includes status, amount, description, and the checkout URL. Its optional provider client-secret field is unpopulated in this flow. |

## Deployment and remaining backend checks

- Serve browser API requests from the bank-web origin. Point its server-only `BANKING_API_BASE_URL` at bank-core. Keep `PAYHERE_SERVER_BASE_URL` on the public HTTPS bank-core origin. The loopback default is only a local example. Keep the merchant secret and signing operation in bank-core. Its provider form contains the merchant identifier and per-order hash required by PayHere.
- In sandbox mode the user's browser posts to `https://sandbox.payhere.lk/pay/checkout` or `/pay/preapprove`. PayHere's servers post back to the exact public bank-core `notify_url` with the original form body. Browser returns and cancels also go to bank-core and follow the configured app deep links. Keep those paths on the core origin at ingress, preserving their methods, query strings, bodies, response status, and content type. Live validation still needs to confirm public DNS and TLS, merchant domain configuration, callback delivery, and the app-link behavior. The frontend tests use a mock and cover the routing boundary only.
- Before enabling wallet UI, fix core's callback validation and replay handling. The checksum covers merchant ID, order ID, amount, currency, and status, but the handlers do not bind the received merchant, amount, or currency to the configured merchant and stored intent or session. Payment notifications update status without deduplication or transition checks. Core uses its own intent/session IDs as `order_id` and does not persist PayHere's `payment_id` in these handlers. Preapproval uses a consumed flag for sequential repeats, but its check and insert lack an atomic single-consumption guarantee. The stored token also needs explicit validation. The intent handler updates metadata only and does not post to a ledger.
- Fix the direct browser handlers before enabling web checkout. Payment return and cancel interpolate the query-supplied intent ID into HTML, and card return passes through a query status that defaults to success. Use safe encoding and treat the browser navigation solely as a return or cancel signal. Confirm expiration and intended access for browser launch links. The checkout handler currently uses the intent ID alone, and the preapproval handler checks only whether the session exists and is unconsumed.
